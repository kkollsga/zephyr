# Zephyr macOS stabilization baseline — updated 2026-07-10

## Verdict

The stabilization program removed every confirmed P0 defect from the initial
baseline. The complete product gate is green: normal, shuffled, race, focused
race-stress, vet, build, coverage, two fuzzers, Staticcheck, benchmarks,
terminal installer upgrade/rollback, documentation consistency, and native
macOS GUI regressions all pass.

Zephyr is now a credible beta candidate for the workflows exercised here. The
application/controller layer has risen from 6.1% to 35.3% statement coverage,
macOS atomic saves preserve symlinks and extended attributes, and the main
large-edit workload is below 1 ms and 1 MiB. It is not yet release-proven:
Save As/overwrite, external reload, clipboard preservation, and tab tear-out
still need end-to-end native automation, and idle memory remains high for a
product positioned as lightweight.

## Fixed defects

### PieceTable race

The lazy line index mutated shared state during supposedly read-only calls.
Line starts are now initialized eagerly and maintained during Insert/Delete, so
concurrent readers do not write shared state. Tests exercise all line APIs
before and after edits and verify newline-boundary invariants. The focused race
test also passed 100/100 repetitions during implementation.

The eager index was subsequently optimized to allocate once, binary-search the
affected line range, and adjust only the affected suffix. The combined
open/index/edit benchmark is now about 0.85 ms and 0.77 MiB rather than
1.5–1.8 ms and 4.10 MiB. Hot line access remains about 16 ns, and the next read
does not pay a hidden rebuild.

### Tree-sitter native retention

Highlighters now deterministically own and close replaced trees, and release
trees, queries, and parsers idempotently. Incremental parsing keeps the edited
old tree alive until its replacement is built. Calls use `ParseCtx` rather than
the deprecated `Parse` API.

One parse previously peaked near 94 MB RSS and 100 parses near 388 MB. After the
fix, one and 100 parses both peak near 93 MB; the three-run benchmark process
peaked near 93 MB instead of roughly 2.40 GB. Full parse time changed about
+2.1% and incremental parse about +5.7% in the focused before/after run.

### Mouse and pointer correctness

The application now:

- ignores secondary and middle presses for primary editing actions;
- preserves and checks pointer identity throughout a gesture;
- clears gesture and hover state on Cancel/Leave;
- includes fractional `Viewport.PixelOffset` in hit testing;
- reverses expanded tab display columns into buffer rune columns;
- renders cursor and selections in display-column space; and
- prevents Markdown read-mode selection from reaching the hidden editor.

Pure coordinate tests cover fractional offsets and tab-column round trips. The
native regression confirms right/middle clicks leave the cursor unchanged,
primary drag selection works, and a seven-pixel scroll is retained.

### Rendering transitions and capture evidence

The original apparent “partial-frame corruption” was a capture-preview false
positive. Raw RGBA PNGs contained complete frames; direct JPEG conversion
dropped translucent Gio layers and made content appear absent. The GUI driver
now composites captures onto an opaque background before producing previews.

A real one-frame lifecycle gap was also fixed: theme changes could clear the
shaper after the frame's renderer initialization. Renderer caches are now reset
as one generation and rebuilt after event processing before drawing. Tests
verify both reset and reconstruction. Native captures cover Vim, Navigator, and
Markdown Read → Edit → Read transitions with complete raw frames.

### Dependencies and static analysis

`golang.org/x/image` was upgraded from v0.26.0 to v0.43.0 (and `x/text` to
v0.38.0), eliminating the four reachable TIFF vulnerabilities in the initial
scan. Govulncheck now reports zero reachable vulnerabilities. Dead helpers,
ineffective code, deprecated parser calls, and the remaining Staticcheck
diagnostics were removed.

### Adversarial parsing and file lifecycle

Two new fuzz targets and deterministic property tests exercise PieceTable edit
sequences and unified-diff parsing. A minimized malformed hunk exposed an
integer-overflow capacity panic; parsing now rejects overflowing coordinates
and changed-line allocation is derived from actual parsed content. The focused
campaign completed more than 6.5 million diff executions after the fix.

File lifecycle tests found and fixed failed-save temp leaks, watcher shutdown
panics, failed Save As path mutation, incorrect reload undo/redo, failed reload
history mutation, lost watches after Save As, and stale highlighters after
changing file type. Watches now track parent directories and filter registered
files, so atomic inode replacement cannot detach them; Save As transfers the
registration without dropping a same-directory watch. Clean buffers ignore
late self-events when disk content already matches memory.

The remaining macOS save-integrity defects were then closed. Atomic saves now
resolve the final symlink target while retaining the editor-visible path,
preserve permissions and extended attributes (including Finder tags), sync the
temporary file and parent directory, and abort before rename when metadata
copying fails. Previously skipped Darwin regressions now run normally.

Documented residual behavior: atomic replacement cannot preserve hard-link
identity, UID/GID ownership, BSD flags, or creation time; new files use private
`0600` permissions; a parent-directory sync error occurs after rename and
therefore cannot roll back the committed content.

## Performance

### Current algorithm benchmarks (Apple M4)

| Operation | Current | Allocation | Initial baseline |
|---|---:|---:|---:|
| Piece single insert | 85.7 ns | 328 B / 6 allocs | 64 ns |
| Piece line access | 14.7 ns | 32 B / 1 alloc | 16 ns |
| Open/index + large insert | 0.851 ms | 0.77 MiB / 6 allocs | 1.56 ms, 4.10 MiB / 30 allocs |
| Open/index + large delete | 0.855 ms | 0.77 MiB / 6 allocs | 1.61 ms, 4.10 MiB / 30 allocs |
| Open/index 100 MiB | 15.5 ms | 12.3 MiB / 3 allocs | not measured |
| Edit + immediate undo, 100 MiB | 0.535 ms | 128 B / 2 allocs | not measured |
| Fuzzy rank, 10k paths | 0.633 ms | 0.844 MiB / 5 allocs | 1.57 ms, 4.01 MiB / 50,022 allocs |
| Tree-sitter full parse | 6.71 ms | 200 B / 4 allocs | 6.57 ms |
| Incremental reparse | 0.736 ms | 248 B / 5 allocs | 0.706 ms |
| Unified diff parse | 0.129 ms | 246 KiB / 1,459 allocs | 0.129 ms |

The fuzzy hot path is 2.3× faster in the controlled five-run comparison, uses
77.9% fewer bytes, and reduces allocations from 50,022 to 5. A reference
implementation and result-isolation tests protect exact scores, byte indices,
Unicode cases, and ranking; a 10-allocation ceiling guards the 10k workload.

The product harness now records window visibility, first submitted frame,
steady frame CPU time, Gio event receipt-to-frame submission, RSS samples, and
soak trends as JSONL/TSV evidence. These are CPU/application measurements—not
physical input-to-photon latency.

The 30-minute native edit/undo/scroll soak passed every configured gate:

| Measurement | Result | Gate |
|---|---:|---:|
| Window visible | 499 ms | ≤1,000 ms |
| Go start → first frame submitted | 316.5 ms | ≤600 ms |
| First-frame CPU | 161.1 ms | report only |
| Steady-frame CPU P95 / P99 | 1.939 / 2.087 ms | P95 ≤8 ms |
| Gio event receipt → submit P95 / max | 0.675 / 5.639 ms | P95 ≤16 ms |
| Steady frames / delivered event samples | 102,060 / 4,429 | ≥500 events |
| RSS start / 5–10 min mean / end / max | 197.6 / 108.3 / 110.0 / 203.0 MiB | max ≤260 MiB |

Across five separate isolated-profile launches, mean Go start-to-first-submit
was 258.1 ms (229.3 ms after the first run), mean window visibility was
389.0 ms, and mean early RSS was 165.2 MiB. The coldest run submitted its first
frame in 373.4 ms; all five remained below the 600 ms regression gate.

RSS did not run away: five-minute means after warm-up were 108.3, 109.1,
109.4, 109.7, and 109.8 MiB. The second-half fitted trend was still mildly
positive at about 2.6 MiB/hour, so the result is stable enough for beta but does
not close the idle/long-session memory optimization target.

## Re-running

```sh
make baseline
```

Live fuzzing is opt-in locally because it uses subprocess workers:

```sh
make fuzz
# or include it in the baseline:
ZEPHYR_RUN_FUZZ=1 make baseline
```

The product baseline intentionally keeps security scanning separate. It can be
included explicitly when that audit is in scope:

```sh
ZEPHYR_RUN_SECURITY=1 make baseline
```

For only the native macOS program:

```sh
make gui-test-regression
```

For launch/frame/RSS evidence and a 30-minute native interaction soak:

```sh
make perf
ZEPHYR_PERF_RUNS=1 ZEPHYR_PERF_INTERACT=1 \
  ZEPHYR_PERF_SOAK_SECONDS=1800 make perf
```
